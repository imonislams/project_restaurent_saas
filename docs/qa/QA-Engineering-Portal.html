Severity reasoning for QA-A-01 — High, not Critical

To flip a payment the attacker needs the reference of a pending payment. process() requires an approved status and a matching reference, then looks the payment up by reference alone. The auditor could not statically find a route that exposes a pending reference to an unauthenticated diner — the dining-tracking payload exposes totals and payment options, not references. The control was broken; the final step was not shown to be reachable. That distinction is why this is High and not Critical, and it is the reason the rating is defensible.

Residual exposure path to watch

If a payment reference ever appears in a redirect URL, receipt, invoice PDF or customer-facing status page, the last step becomes reachable and this finding becomes Critical retrospectively. The fix is already in place, so the exposure is closed — but the invariant matters: a verifier that cannot verify must return false, and no pending reference should be public.

CSV formula injection — mechanics

Exports wrote tenant-controlled text directly through fputcsv. A cell beginning with =, +, - or @ is evaluated by Excel, LibreOffice and Sheets. The realistic path is a platform admin exporting the tenant list and opening it — a routine workflow, which is what raised this above theoretical. The fix is a single neutraliser applied to every export site; numeric cells are passed through untouched so amounts stay numeric. Record: QA-A-06.

Manager-PIN approval control (QA-A-08)

Audit-time behaviour

ManagerPinService::verify() looped over PIN-bearing candidates and called Hash::check() with no attempt counter, no throttle and no lockout. The void route carried only permission:orders.void. Every failure wrote an audit row; nothing stopped the next attempt.

Exposure: a 4-digit PIN is 10,000 combinations. bcrypt at BCRYPT_ROUNDS=12 still permits several guesses per second per connection. Requires an authenticated staff account with orders.void — which is why it was rated Medium, not High.

Current implementation

  • MAX_ATTEMPTS = 5, LOCKOUT_SECONDS = 300.
  • Key is manager-pin:{tenant_id}:{user_id} — per tenant and user, so one terminal cannot lock out another tenant.
  • Enforced inside the service, so all approval call sites are covered, not just the void route.
  • A successful approval clears the counter; a lockout is audited as approval.pin_locked_out.
  • Verification: temporary suite plus negative control (reverting produced 3 failures).
Design consequence to accept explicitly

A correct PIN presented during the 300-second lockout is refused. That is the intended behaviour, but it means a legitimate manager who fat-fingers five times cannot approve anything for five minutes. If that is unacceptable operationally, the alternatives are a manager-initiated reset or an escalating delay rather than a hard lockout — both are behaviour changes, not tuning.

Branch scope fails closed

BranchScope::apply() converts an empty accessible set into whereRaw('1 = 0'). It never degrades to a wildcard. The branch-switch endpoint re-checks canAccessBranch() even though validation already ran, so a forged branch id cannot rely on a validation gap.

Pint later rewrote static::accessibleBranchIds() to self:: in this class. That is a behavioural difference in general; the class is final, so the two are equivalent here. This was checked rather than assumed — the kind of change a "style-only" label hides.

Unscoped models — design decision, not a defect

Twenty-three models carry tenant_id without a global scope. Two high-risk examples were traced:

  • User — deliberately unscoped: the platform workspace must read users across tenants. Every staff route calls $this->authorize() against UserPolicy::sameTenant(). Cross-tenant PATCH /staff/{id} returned 403; can('view'|'update'|'delete') were all false across tenants.
  • OfflineSyncConflict — unscoped, but its only routes sit behind platform.permission:platform.monitoring.view. Exposure is platform-wide visibility, not cross-tenant data.

This is legitimate but fragile: it depends on every future route remembering to call authorize(). It is recorded as a design risk, not a finding.

The indexes are real; the proof is partial

At ~205 orders per tenant the optimizer sees no benefit from the new orders and stock_movements composites and ignores them. That does not mean they are useless — it means the dataset is too small to demonstrate the win. The auditor says so instead of claiming four wins. Index migration as shipped

Environmental caveat — resolved on 2026-11-15

innodb_buffer_pool_size raised 16 MB → 256 MB

When this audit was written the host ran the XAMPP default of 16 MB — roughly 1/100th of a sane production value — and every latency figure here was inflated by it. It has since been raised and the POS measurement re-run. The query count did not change: 59.1 before and after. Only the storage engine's ability to serve those queries changed, which proves the ceiling was the pool and not the application.

Growth risk that outlives the current dataset

stock_movements gains one row per ingredient per sale — it is the fastest-growing table. At the QA dataset size the report cost is invisible; at 300,000 rows it will not be. This is the correct reason to add the index before it hurts, not a claim of present-day slowness.

Going lower means batching writes or deferring audit/kitchen records to after commit — behaviour changes the auditor declined to make unasked. This is the honest version of the result, and it is the version a reviewer should plan against.

What would actually reduce it further

  1. Defer non-critical writes to after commit — audit rows, kitchen tickets, notifications. Removes work from the locked window but changes failure semantics: a crash after commit could lose the audit row unless it is queued durably.
  2. Batch stock movements per sale — one insert instead of one per ingredient. Requires the shortage check to become a set operation; the block-on-shortage setting must be preserved.
  3. Pre-load payment methods and price rules in the same batched query as products.

None of these were implemented. They are listed so the next engineer does not have to rediscover the boundary between "cheap win" and "behaviour change".

The one that looks attractive and is not

OPT-06 was the auditor's own recommendation, implemented, and measured false. InnoDB holds row locks until COMMIT, so an atomic UPDATE … SET last_number = last_number + 1 does not shorten the contended window — the window is the whole sale transaction either way. It also broke 40 tests because the SQL was MySQL-only against a SQLite suite. Reverted; OrderNumberGenerator is byte-identical to its original. The only lever that works is shortening the transaction (OPT-01).

What a senior reviewer should conclude

The security work is now genuinely closed: all five High findings are fixed with negative controls, isolation passed every probe, the dependency surface is at zero advisories with a blocking CI gate, and the dormant schema trap has been removed rather than documented.
