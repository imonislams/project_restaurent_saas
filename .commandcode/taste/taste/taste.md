## Deployment & release engineering
- Keeps secrets out of version control: database credentials, `.env`/environment files, API keys and user-uploaded data must never be committed to Git, and secrets must never leak into CI logs or development environments. Confidence: 0.65
- Wants separate **development, staging and production** environments, each with its own configuration and credentials; every release is verified in staging before it reaches production. Confidence: 0.6
- Expects releases/upgrades to preserve existing data: applying a new version must keep the database, administrator accounts, environment configuration and uploaded files intact, run only the required migrations, and never repeat first-time setup or overwrite user data. Confidence: 0.55
- Wants deployment to be **atomic and reversible**: versioned release directories with an atomic switch of the live release, post-deploy health/smoke checks, a pre-deploy backup, and a documented rollback/recovery procedure. Confidence: 0.5
- Wants CI/CD to produce a **verifiable versioned production artifact** — a package named like `application-vX.Y.Z.zip` with a checksum and a release manifest, built on tag once quality checks, lint and tests pass, failing the pipeline when required checks do not pass. Confidence: 0.5
- Wants a first-run installation path that checks system requirements, tests the DB connection, writes configuration, runs migrations and creates the initial admin, then self-locks — and refuses to initialize or overwrite an existing production database without explicit safeguards. After setup, install/debug/administration endpoints must not remain exposed, and a manual deployment fallback must stay available when the host cannot support automated deploys. Confidence: 0.5
- Does **not** want a browser-based setup wizard: explicitly asked to remove it ("no need the wizard please remove this"), deleting the `/install` routes, controller, Inertia pages, installer middlewares and their i18n keys, and keeping only the headless `php artisan app:install` installer as the install path. This supersedes the earlier wish for a UI wizard, and the CLI must remain a complete replacement — unattended-friendly (every prompt has a matching option) so it can run from a cPanel Cron Jobs entry on a host with no SSH. Confidence: 0.55
- When setting up deployment, wants the **actual built artifact handed over** — the concrete production ZIP they can upload to the server — not only the packaging scripts/CI config, and expects that package to ship a ready-to-use production `.env.example` template (its absence in the archive is treated as a gap; dotfiles are easy to miss so make it discoverable/documented). Confidence: 0.5
- When a runtime/platform mismatch surfaces at deploy (e.g. the server's PHP is older than the Composer lock requires), prefers to **fix it on the host side** — bump the domain's PHP version and enable the required extensions — over downgrading app dependencies/re-resolving the lock to keep supporting older infrastructure: the zero-app-code-change path is chosen, and the app's declared requirement (composer constraint, requirements checker, docs) should then be made truthful rather than left advertising a version it can't run on. Confidence: 0.5
- Explicitly wants production builds to bypass Composer's platform requirement — asks for the package to be built with `--ignore-platform-reqs` (and to also neutralise the shipped `platform_check.php`) whenever the target host's PHP doesn't satisfy the lock, so they get a deployable zip without touching the dependency set: keep the code/deps, remove the guard, ship the artifact. Confidence: 0.55
- **Cannot run a terminal/SSH on the production server** (cPanel shared hosting) — every server-side procedure (first-run install, upgrading, running artisan/migrations, linking storage) must be executable purely through the host's browser UI (File Manager upload+extract, cron jobs as a command runner, the in-app setup wizard/command runner), not via SSH-only scripts: explicitly "i can not run any terminal in the server". SSH-dependent deployment scripts are not a usable path for them, and they expect the plan to be adapted to that constraint rather than repeated. Confidence: 0.6
- Wants the release package to work with the **document root left at the application root**, with requests routed into `public/` by a shipped root `.htaccess` (rather than depending on the host's document root being pointed at `public/`): explicitly "i want to maintain the /public using .htaccess". The archive must therefore actually contain that root `.htaccess` next to `public/.htaccess` — its absence from the zip is reported as a defect to fix in the packaging step. Reaffirmed when told the document-root change was the only route: "why? i can mage this using the htaccss" — they want the rewrite-file workaround made to work, not the host setting changed. Confidence: 0.65
- Expects a freshly extracted package to install with **no hand-run commands and no hand-created config**: the setup wizard must be able to render on an install that has no `.env` and therefore no `APP_KEY` (bootstrapping whatever it needs itself, e.g. a temporary key and database-free session/cache), and generating `APP_KEY` is the wizard's job — an "No application encryption key has been specified" error on the install page is an installer defect to fix at the root, not a step the user should perform. Confidence: 0.55
- Wants the CI/CD pipeline documented as a written in-repo procedure/runbook — what each stage does, one-time setup (variables, keys, server-side config), the per-release steps, and the rollback command — delivered alongside the actual CI config, not merely explained in chat; explicitly asks "CI/CD implementation process how? what is my procedure". Confidence: 0.55
