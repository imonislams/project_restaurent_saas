# Taste
- Wants work executed **phase by phase**, one approved phase at a time; do not automatically proceed to the next phase — stop after verification and wait for explicit approval. Confidence: 0.95
- Documentation-first: wants project docs (PRD, architecture, roadmap, etc.) produced before writing implementation code. Confidence: 0.85
- Discovery-first: inspect the existing repository (code, DB, routes, auth, frontend, tests, deployment) before making any changes; no broad refactoring during discovery. Confidence: 0.85
- Approves work with terse, blanket affirmatives (e.g. "YES DO", "do it", "yes") rather than detailed instructions; once a phase is greenlit, expects the agent to carry it out end-to-end (implementation, full test suite, formatter/lint, frontend build, live end-to-end verification, written report) without intermediate check-ins. Confidence: 0.8
- Wants a written audit/report per phase: scope, changes, test results, and remaining risks, before moving on. Confidence: 0.7
- Prefers a maintainable **modular monolith** over premature microservices. Confidence: 0.8
- Prefers a Laravel-first stack: Laravel + Inertia.js + React + TypeScript with Tailwind CSS for desktop-style applications. Confidence: 0.75
- Prefers not to rewrite a working system merely to match a preferred stack — preserve existing working behavior unless an evidence-backed defect requires change. Confidence: 0.75
- Prefers business logic in dedicated application/domain services rather than giant controllers. Confidence: 0.7
- Insists that access control (roles/permissions, tenant/branch isolation) be enforced on the backend, not just by hiding UI elements. Confidence: 0.75
- Values data-integrity rigor: DB transactions for critical writes, idempotency keys for retried requests, and append-only/auditable movement ledgers. Confidence: 0.7
- Prefers the main navigation menu in a persistent **sidebar** rather than the top bar. Confidence: 0.8
- Wants clean, de-duplicated navigation: no two menu entries should lead to the same destination, near-duplicate pages should be grouped as in-page tabs rather than separate menu items, navigation sections should be collapsible (accordion), and only one item should show as active at a time. Sections with no visible items (all filtered out by permissions or plan entitlements) must not render as a header with nothing under it — they should be hidden entirely. Confidence: 0.7
- Values self-explanatory information design on summary cards: plan/pricing and similar cards must make the key facts — price, included features, limits — legible at a glance instead of requiring interpretation. Confidence: 0.6
- Expects a polished, "advanced" desktop-style UI/UX (dashboard, sidebar shell, visual refinement) — a functionally correct but bare-bones interface is not enough, and will explicitly reject a functionally working UI as "too poor" if the design is not refined. Confidence: 0.8
- Cares specifically about the design quality of interactive controls — buttons, form fields, labels/hints/inline errors, filters and page headers — with consistent variants, sizes, spacing and focus/active states across the whole app. Confidence: 0.7
- Prefers a restrained, "engineered" visual style for admin/business UIs and explicitly rejects excessive gradients, oversized KPI cards, excessive rounded corners, decorative illustrations, unnecessary animation, heavy shadows, huge empty spaces, rainbow palettes, glassmorphism, and generic landing-page layouts. Confidence: 0.85
- Insists status never be communicated by color alone (always pair color with a label/icon), and wants accessible admin UIs: keyboard navigation, visible focus states, accessible labels, adequate contrast, screen-reader-friendly messaging. Confidence: 0.75
- Demands honesty about implementation state: do not use static/mock data to stand in for working backend features, do not display fabricated or static metrics/health indicators, mark unimplemented features clearly, and report known limitations rather than presenting a finished-looking screen as proof a feature works. Confidence: 0.85
- Wants secrets handled carefully: encrypt credentials at rest, never display full secrets after saving, mask them in forms/logs/exports, and never expose credentials/API keys to the frontend. Confidence: 0.8
- Insists payments/payment-like flows be verified server-side: never treat a browser redirect or a return to a success URL as proof of success, verify amounts/currency/identity with the provider, and process notifications idempotently. Confidence: 0.8
- Values immutable financial records: never hard-delete or silently rewrite finalized invoices/payments, correct them via credit notes or controlled adjustments with an audit trail, and avoid double-counting across reports. Confidence: 0.75
- Prefers server-side pagination/filtering for large tables and does not want full histories (tenants, invoices, payments, logs) loaded into the browser. Confidence: 0.7
- Expects an audit trail for sensitive/admin actions capturing actor, action, target, timestamp, reason, and result. Confidence: 0.75
- Prefers external integrations (payment gateways, email/notification providers, etc.) placed behind an abstraction/pluggable interface so additional providers can be added without rewriting core business logic — do not hard-code a single provider into the core. Confidence: 0.75
- Prefers long-running work (backups, restores, bulk sends, reconciliation, report exports) executed asynchronously via queued background jobs with retries, timeouts, idempotency, and monitoring — and expects queued work reported as complete only when it actually is (dispatched ≠ completed). Confidence: 0.7
- Expects automated feature/integration tests to accompany every feature as part of the definition of done — a feature is not complete without passing tests and verification. Confidence: 0.75
- Insists on precise, documented financial semantics: distinct money concepts (invoiced, collected, outstanding, recognized revenue, refunds) must never be conflated, and amounts in different currencies must never be summed without a documented conversion method. Confidence: 0.75
- Prefers defensive/fail-safe handling of cross-cutting infrastructure: secondary concerns (logging, settings/config lookups, mail transport config, event listeners) must never break the primary request or business flow — wrap them so failures are swallowed and fail closed to safe defaults. Confidence: 0.7
- Wants business/reporting dates resolved in the tenant's local timezone rather than UTC, so date-bucketed data (expenses, periods, reports) stays consistent across the UTC/local day boundary. Confidence: 0.65
- Distinguishes configured state from verified operation: a declared schedule/configuration is not proof something ran — record and surface actual executions (heartbeats, run history) rather than presenting configuration as evidence. Confidence: 0.65
- Prefers destructive/irreversible operations (full-platform or tenant restores, bulk deletes) to be strongly guarded rather than exposed as one-click buttons — require explicit typed confirmation, take a pre-action safety checkpoint, and keep the most dangerous operations as documented manual procedures rather than a UI action. Confidence: 0.6
- Prefers the **Roboto** font as the UI typeface (do not default to Figtree/other Tailwind defaults); explicitly requested it. Confidence: 0.85
- Wants to be able to run framework/build commands (all Laravel artisan commands and npm/Node commands) from within the system UI itself, not only from an external terminal. Confidence: 0.7
- Wants every module developed to an equally "advanced"/complete standard — does not accept basic or placeholder functionality lingering in some modules while others are polished. Confidence: 0.65
- Prefers admin-managed content (email templates/notifications and similar) to be editable from the UI with live preview and a test-send, rather than being read-only or hard-coded. Confidence: 0.6
- For cross-cutting/branding concerns, prefers a single **platform-admin (super-admin) managed global setting applied to all tenants** rather than per-tenant configuration — explicit example: receipt branding is controlled centrally by the platform admin for every restaurant. Confidence: 0.6
- Keeps the **SaaS provider's own identity** strictly separate from the tenant's: when they say "company branding" in a multi-tenant context they mean the platform/provider branding (platform name, provider logo, support contacts, tagline, website), not the tenant/restaurant's details — explicitly corrected the agent for using tenant branding where provider branding was wanted. Confidence: 0.75

Confidence: 0.7

Confidence: 0.6

Confidence: 0.8
